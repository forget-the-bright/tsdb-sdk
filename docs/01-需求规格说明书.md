## 1. 文档目的

本文把“多个数据库集成到一套 SDK”这一原始诉求，拆解为可评审、可验收的需求。它回答四个问题：

1. 为什么要做（背景与问题）；
2. 做给谁用、在什么场景用（角色与场景）；
3. 必须做到什么（功能/非功能需求）；
4. 做到什么程度算完成（验收标准）。

本文**不**描述具体实现细节；实现见 `docs/03` 与 `docs/04`。

## 2. 背景

### 2.1 现状

- 现场已使用**和利时（HLS）**与 **GE Proficy Historian** 两套工业时序数据库，各自有 REST SDK 参照实现：
  - `reference\HLS_REST_SDK`：43 个 Java 文件、约 2926 行，4 个业务接口；
  - `reference\GE_REST_SDK`：62 个 Java 文件、约 8079 行，92 个 REST 端点（另有 OAuth 令牌接口）。
- 两套 SDK 均为 Java 8 + Spring Boot 2.7 的“可嵌入 Starter 风格”jar，Apache-2.0。
- 两套 SDK 的 `ApiClient`、`TokenHolder` 都使用**静态字段**保存配置与令牌，同一 JVM 只能有一个实例。
- 两套 SDK 的模型、认证、质量码、时间格式、返回结构均不同：
  - HLS：`BaseResult{code,msg}`，质量码 `GOOD=1`，宽表（AVG/MIN/MAX/Bound 多列），仅实时值 + 区间聚合 + 全量标签；
  - GE：`BaseResult{ErrorCode,ErrorMessage}`，质量码 `GOOD=3`，长表 `Samples[]`，支持原始/插值/采样/趋势/写入/标签管理。

### 2.2 缺口

- **横河（Yokogawa）**：尚无 SDK；现场 DCS 若为 CENTUM 系列，期望直接集成。
- **IoTDB**：尚无 SDK；期望作为厂级汇聚/分析存储。
- **公共层缺失**：每接一个库就要重写一套调用代码，无法平滑切换。
- **安全与可用性基线缺失**：超时、重试、熔断、密钥管理、TLS、审计均未统一。

### 2.3 原始诉求（用户原话要点）

> 多个数据库集成到一套 SDK 包里面，每个数据库独立包目录，自己的方法封装好；对比各个数据库，抽取相同点，做公共方法层，方便后续切换。配置文件控制集成数据库类型。集成好后原生方法和公共集成方法都可以使用。和利时、GE 目前已有 SDK；欠缺的是横河以及 IoTDB。数据库选型目前最好的选择是横河，因为可以和 DCS 直接集成。核心权衡点是可用性和安全性。

## 3. 角色与使用场景

### 3.1 角色

| 角色 | 关注点 | 与本产品的关系 |
|---|---|---|
| 集成开发工程师 | 调用简单、模型统一、换库成本低 | 主要使用者 |
| 现场运维工程师 | 配置、健康检查、故障定位 | 部署与排障 |
| 安全/网络管理员 | 凭证、TLS、网段隔离、审计 | 安全评审与放行 |
| 业主 DCS 负责人 | 不影响 DCS 稳定运行、只读优先 | 横河接入审批 |
| 数据分析/上层应用 | 历史数据可获取、格式统一 | 间接受益者 |
| SDK 维护者 | 新增数据库成本低、契约可测 | 架构与代码质量 |

### 3.2 典型场景

**S1 新站点只有横河 DCS。** 配置一个 `yokogawa` 实例，通过 OPC UA 读取实时值与历史值；业务代码只依赖公共接口。

**S2 既有 HLS/GE 现场。** 保留原有原生调用（历史代码不动），新代码使用公共接口；两套方式可同时存在。

**S3 多库对比/迁移。** 同一段查询代码，仅切换 `tsdb.default-instance`，即可在 HLS/GE/横河/IoTDB 之间对比结果与性能。

**S4 厂级汇聚。** 从 HLS/GE/横河读取数据，写入 IoTDB 做长期存储与分析；SDK 同时持有多个实例。

**S5 故障降级。** 主库不可用时，读请求按配置回退到备库/缓存，并明确标记数据来源与新鲜度。

## 4. 目标

### 4.1 业务目标

- 新现场接入周期从“每库一套代码”降为“加一个配置 + 选一个驱动”。
- 同一业务代码可在至少 3 种数据库间切换，切换成本 ≤ 1 人日（不含数据模型差异）。
- 横河场景具备可演示的 DCS 直连 POC，安全方案通过业主/网络评审。
- 形成可复用的 SDK 产品，而不是一次性项目代码。

### 4.2 产品目标

- 一套 Maven 多模块 SDK：公共层 + 4 个驱动 + Starter + Testkit。
- 统一模型：标签、样本、质量、时间、类型、单位、错误。
- 统一配置：`tsdb.*` 管理多实例、启用/禁用、默认实例。
- 原生逃生口：任何厂商特有能力都能调用。
- 能力协商：不支持的能力在调用前可知、调用时明确报错。

### 4.3 技术目标

- 去静态单例，支持同 JVM 多实例、多库并存。
- 公共层零厂商依赖；驱动之间互不依赖。
- Java 8 字节码兼容，Spring Boot 2.7 基线，可选 Boot 3 适配。
- 默认安全：只读、TLS 校验、密钥外置、写审计、依赖无已知高危 CVE。

## 5. 范围

### 5.1 范围内（In Scope）

- HLS、GE 两套参照 SDK 的收口与重构（保留原生能力）。
- 横河 Yokogawa 驱动（OPC UA 优先；Exaquantum 备选）。
- IoTDB 驱动（Session API 优先；REST 备选）。
- 公共 API、模型、能力、异常、配置、SPI。
- Spring Boot Starter、健康检查、指标。
- 契约测试套件、Mock Server、示例工程。
- 能力矩阵、迁移指南、安全基线文档。

### 5.2 范围外（Out of Scope）

- 不做 DCS 控制逻辑（不开环、不做 PID、不下发控制指令）。
- 不做历史数据的大规模迁移/清洗（可作为后续独立项目）。
- 不做 BI/报表/大屏（由上层应用负责）。
- 不替代厂商 historian 的采集器/报警服务器。
- P1/P2 不做跨库分布式事务；写入一致性按单库保证。
- 不承诺与旧 SDK 的二进制兼容（源码级迁移指南 + 适配层）。

## 6. 功能需求

优先级：P0 = v1.0 必须；P1 = v1.x 重要；P2 = 后续增强。

> 注意：本章的 P0/P1/P2 是**需求优先级**，与 `docs/05` 的**实施阶段编号**（P0 设计、P1 公共层、P2 IoTDB、P3 横河、P4 路由）不是同一套编号；实施排期以 `docs/05` 为准。

### FR-01 统一客户端与实例管理（P0）

**需求**：提供 `TsdbClient` 作为统一入口，按实例名获取；每个实例拥有独立配置、认证、缓存、线程池与指标标签；支持运行时创建/关闭多个实例。

**验收**：
- 同一 JVM 同时创建 `hls_main`、`ge_main`、`iotdb_historian` 三个客户端，互不干扰；
- 关闭一个实例不影响其他实例；
- 实例名重复创建有明确错误或返回同一受管实例（二选一并写入文档）。

### FR-02 配置驱动装配（P0）

**需求**：通过 `tsdb.*` 配置声明实例类型、连接参数、认证、超时、缓存、能力开关；支持 `enabled=false` 禁用；支持 `default-instance`。

**验收**：
- 仅改 YAML 即可从 HLS 切到 GE，业务代码不变；
- 未知 `type` 启动失败并给出可用类型列表；
- 缺少必填项时启动失败，错误信息指出实例名与字段名；
- 敏感字段支持 `${ENV_VAR}` 占位，日志不出现明文。

### FR-03 每库独立驱动模块（P0）

**需求**：每个数据库一个 Maven 模块与独立 Java 包；驱动只依赖 `tsdb-sdk-common` 与本库客户端；可按需引入，不引入的库不加载。

**验收**：
- 只引入 `tsdb-sdk-hls` 时，classpath 无 GE/横河/IoTDB 的类；
- 驱动目录内可独立编译、独立单测；
- 公共层 `pom.xml` 不出现任何厂商依赖。

### FR-04 原生 API 逃生口（P0）

**需求**：公共接口之外，必须能拿到厂商原生客户端/Invoker，调用其全部方法；原生调用不经过公共层的模型转换。

**验收**：
- `client.unwrap(HlsNativeApi.class)` 返回可用对象；
- 用原生方法完成一次公共层不支持的操作（例如 GE 标签属性更新、HLS 原始请求）；
- 文档明确“原生调用绕过能力校验与质量归一，风险自担”。

### FR-05 标签目录（P0）

**需求**：统一 `TagCatalog`：列出、按名称模式检索、按标签名获取详情、判断存在；返回 `TagInfo`（名称、描述、数据类型、工程单位、厂商属性）。

**验收**：
- HLS 全量标签可分页/分批读取，不因标签多而 OOM；
- GE 支持名称掩码与分页；
- 横河支持 OPC UA Browse（含命名空间）；
- IoTDB 支持按设备/测点 SQL 检索；
- 标签名大小写、特殊字符行为在驱动文档中写明。

### FR-06 实时值（P0）

**需求**：一次读取多个标签的当前值，返回带时间戳、质量、类型、单位的样本；保持请求顺序或提供 tag→sample 映射。

**验收**：
- 一次 1000 个标签，返回与厂商工具一致（抽样比对）；
- 不存在的标签有明确错误/空值语义，不整体失败；
- 质量码归一正确（HLS 1、GE 3 均映射 GOOD）。

### FR-07 原始历史（P0/P1）

**需求**：按时间范围、方向、最大点数读取原始样本；支持正序/倒序；支持分页/截断提示。

**验收**：
- GE `raw`、IoTDB SQL、横河 HDA 可用；
- HLS 明确返回 `UNSUPPORTED`，错误信息说明“HLS 仅支持区间聚合”；
- 时间边界左闭右开或闭区间在文档中统一并测试。

### FR-08 聚合历史（P0）

**需求**：按时间范围 + 间隔 + 聚合函数（AVG/MIN/MAX/SUM/COUNT/FIRST/LAST/BOUND）读取；返回每个标签的时间序列。

**验收**：
- HLS 的宽表正确拆为长表，AVG/MIN/MAX/Bound 分别映射；
- HLS 未返回 `Quality_AVG`，AVG 结果质量置 `UNKNOWN` 并标注来源，不得猜测为 GOOD；
- 修复参照实现中 MAX/MIN 参数写反的缺陷（不得直接复用有缺陷的 `buildRequest`）；
- GE 用 `calculated`/`sampled` 实现，结果与厂商工具抽样一致；
- 空区间返回空列表而非 null。

### FR-09 插值/采样/趋势（P1）

**需求**：支持线性/前值插值、按数量或间隔采样、趋势查询；不支持的库显式报错。

**验收**：
- GE `interpolated`/`sampled`/`trend` 可用；
- IoTDB 用 `fill`/降采样 SQL 实现；
- 横河若 HDA 不支持插值，则由客户端在原始点上补插值，并在结果中标记 `derived=true`；
- HLS 返回 `UNSUPPORTED`。

### FR-10 写入（P1，默认关闭）

**需求**：支持批量写入样本（时间戳、值、质量）；默认配置 `allow-write=false`；开启后需显式传入写会话；写入失败可定位到标签/批次。

**验收**：
- GE `create`、IoTDB `insertRecords/insertTablet` 可用；
- HLS/横河按能力声明，不支持则明确报错；
- 写操作产生审计日志（实例、标签数、时间范围、调用方、结果），不含敏感值；
- DCS 直连默认禁止写。

### FR-11 能力协商（P0）

**需求**：每个客户端暴露 `CapabilitySet`；公共方法在执行前检查能力；不支持时抛 `TsdbUnsupportedException`，携带能力名与库类型。

**验收**：
- `capabilities().supports(RAW_HISTORY)` 可查询；
- 对 HLS 调用 `readRaw` 抛明确异常，不产生 HTTP 请求；
- 能力矩阵由驱动声明并与文档一致，契约测试校验。

### FR-12 模型归一（P0）

**需求**：统一时间（`Instant`，UTC）、质量（`Quality`）、值类型（`ValueType`）、工程单位、标签描述；保留厂商原始码/原始类型用于追溯。

**验收**：
- HLS `TagValueTime`（毫秒）→ `Instant`；
- GE `"yyyy-MM-dd HH:mm:ss"` 按配置时区解析（默认 `Asia/Shanghai`），DST 有测试；
- 质量映射表覆盖所有厂商码；
- 未知厂商码映射 `UNKNOWN` 且保留原码，不丢失信息。

### FR-13 统一错误模型（P0）

**需求**：配置、连接、认证、超时、限流、查询、数据、不支持能力等错误有统一异常类型与错误码；区分可重试/不可重试；保留厂商原始错误码与消息。

**验收**：
- 调用方只捕获 `TsdbException` 即可分类处理；
- 401/403 不重试；超时/5xx 可按策略重试；
- 日志包含实例、操作、耗时、厂商码，不包含密码/token。

### FR-14 健康检查与可观测（P1）

**需求**：每个实例提供健康状态（UP/DEGRADED/DOWN + 原因 + 最近成功时间）；Micrometer 指标：请求数、错误数、延迟、在途数；Spring Boot Actuator 健康指示器。

**验收**：
- 断网/认证失败/正常三种状态可区分；
- 指标带 `instance`、`type`、`operation` 标签，基数可控；
- 健康检查本身有超时，不拖垮应用。

### FR-15 兼容旧配置与旧调用（P1，规划）

**需求**：支持 `hls.datacollection.*`、`ge.datacollection.*` 旧前缀映射到新模型；提供旧 Invoker 风格的适配器（源码级迁移）。当前版本尚未实现旧前缀自动映射，迁移时需手工改写为 `tsdb.*`。

**验收**：
- 旧 YAML 不改可启动（单实例场景）；
- 旧代码替换 import 后可编译运行；
- 迁移指南列出不兼容点（静态方法、返回模型、质量码）。

### FR-16 横河接入（P1/P2）

**需求**：支持 OPC UA（DA + HDA）作为首选；支持证书/安全策略配置；支持 Browse 命名空间；Exaquantum 作为备选路径。

**验收**：
- 现场 POC 读取至少 100 个 DCS 标签的实时值与 24h 历史；
- `SignAndEncrypt` + `Basic256Sha256`（或现场要求策略）连通；
- 断线自动重连，重连期间请求快速失败而非挂死；
- 形成《横河接入 POC 报告》，含版本、端口、证书、标签命名、性能、限制。

### FR-17 IoTDB 接入（P1）

**需求**：Session API 优先（SessionPool 多节点），REST 备选；树模型/表模型二选一或都支持；支持写入、原始查询、聚合、最新值、标签检索。

**验收**：
- 单机与集群（如可用）均连通；
- 批量写入 10 万点可控时间内完成；
- 查询超时/会话失效有明确错误与重连；
- SQL 拼接受标签名白名单/转义保护。

### FR-18 安全控制（P0）

**需求**：默认只读；写能力显式开启；凭证外置；TLS 默认校验；敏感信息脱敏；写操作审计；依赖漏洞扫描。

**验收**：见 NFR-S1~S7。

### FR-19 多实例路由/回退（P2）

**需求**：可按标签前缀/标签组路由到不同实例；可配置主备回退；结果标记来源实例与数据新鲜度。

**验收**：
- 同一逻辑标签名在不同库中可映射；
- 主库超时后按策略回退，回退可关闭；
- 不产生写放大或重复写。

### FR-20 文档、示例、测试套件（P0）

**需求**：可运行 sample（每个库至少 1 个）、完整配置参考、能力矩阵、迁移指南、契约测试套件。

**验收**：
- 新开发者按 README 30 分钟内跑通一个库的读取；
- 契约测试对 4 个驱动可复用；
- 文档中的代码片段可编译（CI 校验）。

## 7. 非功能需求

### 7.1 可用性（Availability）

| ID | 需求 | 验收 |
|---|---|---|
| NFR-A1 | 所有网络调用必须有连接/读取超时，禁止无限等待 | 默认 connect 5s / read 30s，可配；测试注入延迟验证 |
| NFR-A2 | 仅对幂等读操作重试，指数退避 + 抖动，默认最多 2 次 | 401/400 不重试；超时/503 重试；日志可追踪 |
| NFR-A3 | 每实例隔离线程池/并发上限，单库故障不拖垮全局 | 一个实例慢查询占满时，其他实例仍可服务 |
| NFR-A4 | Token 过期/失效自动刷新，刷新单飞（single-flight） | 并发 50 请求仅触发 1 次刷新 |
| NFR-A5 | 支持熔断/快速失败（可选启用） | 连续失败后短路，恢复半开 |
| NFR-A6 | 标签目录可缓存，读失败时可返回上次成功快照并标记 stale | 断网时目录仍可读，标记清晰 |
| NFR-A7 | 优雅关闭：停止接收新请求，等待在途请求，释放连接 | 关闭 5s 内完成，无泄漏 |

> SDK 不承诺数据库本身的 SLA；承诺“故障时行为可预期、可观测、可恢复”。

### 7.2 安全性（Security）

| ID | 需求 | 验收 |
|---|---|---|
| NFR-S1 | 禁止硬编码凭证；支持环境变量/密钥文件/外部密钥管理 | 代码扫描无明文密码；日志脱敏 |
| NFR-S2 | TLS 默认校验证书与主机名；禁止默认 trust-all | 自签证书需显式配置 trust-store；测试握手失败 |
| NFR-S3 | 最小权限：默认只读账号；写能力需显式开关 + 独立凭证 | 只读账号无法写入；写开关默认 false |
| NFR-S4 | 写/管理操作审计：谁、何时、哪个实例、多少点、结果 | 审计日志可检索，不含值 |
| NFR-S5 | 公共层 JSON 统一 fastjson 1.2.83（AutoType 关闭、safeMode、只做树解析）；不引入 Jackson 等其他 JSON 库；依赖扫描 | OWASP dependency-check 无 high/critical |
| NFR-S6 | 输入校验：标签名、时间范围、批量大小、SQL 拼接 | 注入用例被拒绝；超限有明确错误 |
| NFR-S7 | OPC UA 证书生命周期管理：申请、信任列表、轮换、吊销 | POC 文档含证书步骤；过期前告警 |
| NFR-S8 | 跨网段部署：支持代理/网关模式，DCS 网段不直接暴露给应用网 | 网关模式可部署；防火墙矩阵文档化 |

### 7.3 性能（Performance）

| ID | 需求 | 目标 |
|---|---|---|
| NFR-P1 | 批量实时读 1000 标签（LAN） | p95 ≤ 2s（受厂商接口限制，需实测） |
| NFR-P2 | 单标签 24h 原始点（1s 采样，8.6 万点） | p95 ≤ 5s，内存峰值 ≤ 64MB |
| NFR-P3 | 并发查询 | 每实例默认 8 并发，可配；无交叉阻塞 |
| NFR-P4 | SDK 自身开销 | 序列化/转换 CPU 占比 < 20%，常驻内存 < 256MB |
| NFR-P5 | 大批量标签目录 | 10 万标签分页加载，不 OOM |

### 7.5 可维护性（Maintainability）

| ID | 需求 |

### 7.6 可观测性（Observability）

- 追踪：可选 OpenTelemetry span，标签含实例与操作，不含标签名全量（基数控制）。

## 8. 约束与假设

### 8.1 约束

1. 现场多为内网/离线环境，不能依赖公网服务。
2. DCS 网段有严格分区，应用不能直连控制网；需网关/防火墙策略。
3. 横河资料可能受 NDA 限制，具体接口以现场版本为准。
4. 既有 HLS/GE SDK 为 Apache-2.0，可复用/修改，但需保留许可证与版权声明。
5. 客户现场 JDK 可能仍为 8，故基线 Java 8。
6. 项目周期与人力有限，按 P0→P3 分批交付。

### 8.2 假设

1. 现场可提供 HLS/GE/横河/IoTDB 的测试实例或 Mock。
2. DCS 侧允许只读账号，且允许从指定跳板/网关访问 OPC UA 端口。
3. 标签命名规范由业主提供；SDK 不做语义推断。
4. 各服务器时间已 NTP 同步；SDK 仍按配置时区解析厂商本地时间。
5. 写入不是一期刚需；默认关闭不影响验收。
