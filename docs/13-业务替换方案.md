## 1. 概述与范围

### 1.1 本轮做什么、不做什么

- **数据源不变**：业务仍读 GE Proficy Historian，只是把自研 `GE_REST_SDK`（`io.github.forget_the_bright.ge.*`）换成通用 `tsdb-sdk`（`io.github.forget_the_bright.tsdb.*`）的 GE 驱动。不是换数据库。
- **本轮已交付**：SDK 对齐改造 + 生产只读一致性裁决 + 本替换方案文档。
- **本轮不动业务代码**：`reference/tl-back-enfi` 只读，作为基准与文档输入。下表所有“改造状态”均为 **待改造**。
- **不做同名兼容层**（用户拍板）：不提供 `DataApiInvoker`/`ApiUtil`/`SampledEntity` 同名适配。`TsdbClient` 保持通用、简单，只覆盖项目常用查询；业务代码后续重写为公共 API 调用，厂商特有能力走 `unwrap(GeNativeApi.class)` 原生逃生口。
- **2026-11-18 修订（重要）**：初版把 3 类调用映射错了，本版已改：
  1. `getHistorianIntervalValueBySampled` / `getHistorianIntervalValueByInterpolated` 返回的是**逐间隔累计差值**（相邻样本相减），不是采样/插值曲线；
  2. `getSampledByRequestParamPost` 不能按符号一刀切：`Calculated+SumValue` 的 42 处调用应走整窗 `INTERVAL_SUM` 或原生 `SumValue`，初版错写成 `SAMPLED`；
  3. 差分时间戳沿用驱动返回的桶样本时间，初版“时间戳=间隔结束时刻”没有实现依据（IoTDB `GROUP BY` 返回桶起点；HLS/GE 未统一确认）。

### 1.3 SDK 对齐改造结论（本轮已完成）

| # | 改造项 | 结论 |
|---|---|---|
| 1 | 历史/当前值底层 GET→POST | `readRaw/readAggregated/readInterpolated/readCurrentRawValue` 全改 POST，body 明文 `tagNames`（分号拼接），大批量 tag 不再超 URL 长度；GET 版本保留为原生逃生口与对比基准 |
| 2 | SAMPLED 语义 | 公共 `SAMPLED` → POST `/v1/datapoints/sampled`（samplingMode=2,queryModifier=1），不再是 calculated+19 的错位实现 |
| 3 | SUM 聚合映射 | `Aggregation.SUM` → CalculationMode **9（RawTotal，算术和）**；旧文档误写 24（SumValue=末−首）已纠正 |
| 4 | INTERVAL_SUM | 新增 `Aggregation.INTERVAL_SUM`，复刻旧 `getIntervalValueBySumTag`：2×POST calculated(17/19,count=1,intervalMs=1)，BigDecimal 末−首 |
| 5 | per-tag 错误码 | `TagSample.attributes` 携带 errorCode/errorMessage/dataType/engineeringUnits/量程；sample=null 且 errorCode≠0 表示该位号出错（区分“无值”与“出错”） |
| 6 | 差分基线 | N 次单 tag GET raw → 主查询扩一个间隔折叠（`count+1`，首桶即基线，1 次 calculated 请求）；扩展桶为空才补 1 次批量 POST raw（Backward,count=1） |
| 7 | 时间语义 | 生产实证旧 SDK 输出**真 UTC**（hutool UTC_FORMAT 绑定 UTC），新 SDK 默认 UTC/UTC 正确；伪 UTC（GMT+8 墙钟+字面 Z）会 +8h 错位，已删除该预设 |
| 8 | 能力声明同步 | `GeDriver.CAPABILITIES` 与 `GeClient` 一致（7 项），单测断言两处集合相等 |

### 1.4 生产只读一致性裁决（GeComparisonIT，2026-11-12）

同 tag 同窗口，旧 `GE_REST_SDK`（test scope 引入）vs 新 `tsdb-sdk` 逐点比对时间戳/值/质量码/units/per-tag ErrorCode：

```text
[SUMMARY] MATCH=2021  DIFF=0  OLD_ONLY=0  NEW_ONLY=0  PROBE=481
```

- **主契约全 MATCH**：7 种聚合（AVG/MIN/MAX/COUNT/FIRST/LAST/SUM↔1/4/5/6/17/19/9，各 24 点）、sampled 曲线（24 点）、interpolated 曲线（24 点）、raw-backward（50 点）、当前值（真标签逐字节一致 + 缺失位号 n=0）、interval-sum（_SUM=4476.2542 / _PV=-1.29551125）、标签目录（ErrorCode=11,n=5）、时间 A(旧)vsB(新真UTC)（50 点）。
- **2000 tag 批量**：单请求 POST 两侧全成功（new 4125ms / old 4412ms，matched=2001 differed=0）；GET 对照组 HTTP **414**（URL 超长）失败，记录为“必须 POST”的证据。
- **469 个批量漂移标签**：经单标签紧挨复读证实为活数据在动（快更新电气测量块约 16s 归档周期），非 SDK 差异；稳定可复现差异仍保留 DIFF。
- **4 个 verdict=DIFF 全是反证探针**：伪 UTC +8h ×2、24(SumValue)≠17/19 ×2，用于证明语义边界，非主契约失败。
- **只读守卫**：IT 内禁止 create/write/delete/启停采集器/告警恢复端点。凭据放 gitignore 的 `ge-it.properties`，不入库不打印。

> 结论：公共 API 能查出与旧 SDK **一致的数据**，DIFF 已归零。下方映射可据此放心落地。

## 2. API 映射表（6 类查询 + 完整符号字典）

业务用法收敛为 6 类查询。每类给出旧线缆→新公共 API 的 before/after。新 API 签名均已对照源码核实；`client` 为 `TsdbClient`，`ge` 为 `client.unwrap(GeNativeApi.class)`。

### 2.1 实时值（getCurrentValuePost / sampled samplingMode=1）

```java
// before —— 旧 SDK
DataResult r = DataApiInvoker.getCurrentValuePost(new TagNamesEntity().setTagNames("AI-101;AI-102"));
String v = ApiUtil.convertOneDataByTagNames(r.getData()).get("AI-101");

// after —— 公共 API
List<TagSample> cur = client.currentValues().read(Arrays.asList("AI-101", "AI-102"));
for (TagSample ts : cur) {
    Sample s = ts.getSample();                 // 缺失位号 s==null
    String err = ts.getAttributes().get("errorCode");  // ≠0 表示该位号出错
    // 业务侧适配器：Sample→业务值（BAD→默认值等 quirk 原样保留）
}
```

线缆：POST `/v1/datapoints/sampled`，body `{"samplingMode":"1","queryModifier":1,"tagNames":"AI-101;AI-102"}`（明文）。

### 2.2 插值曲线（getInterpolatedByRequestParamPost / sampled samplingMode=2）

```java
// before —— 旧 SDK（interpolated 端点，75 处）
DataResult r = DataApiInvoker.getInterpolatedByRequestParamPost(
        new TagNamesEntity().setTagNames("AI-101"), start, end, 24, 3600_000L);

// after —— 公共 API（INTERPOLATED）
List<TagSeries> series = client.history().read(HistoryQuery.builder()
        .tags("AI-101").range(start, end)
        .mode(QueryMode.INTERPOLATED)
        .interval(Duration.ofHours(1))
        .build());

// before —— 旧 SDK（sampled 端点 samplingMode=2，GeUtil 主流曲线路径）
DataResult r2 = DataApiInvoker.getSampledByRequestParamPost(new SampledEntity()
        .setSamplingMode(SamplingMode.Interpolated).setQueryModifier(1L).setTagNames("AI-101")
        .setStart(start).setEnd(end).setIntervalMs(3600_000L));

// after —— 公共 API（SAMPLED）
List<TagSeries> s2 = client.history().read(HistoryQuery.builder()
        .tags("AI-101").range(start, end)
        .mode(QueryMode.SAMPLED)
        .interval(Duration.ofHours(1))
        .build());
```

> **裁决说明**：interpolated 端点与 sampled(samplingMode=2) 是两条不同线缆。生产对比已分别验证各自与旧 SDK 一致；替换时**按调用点原线缆选模式**（原 interpolated→INTERPOLATED，原 sampled-2→SAMPLED），不可混用。

### 2.3 服务端聚合（getCalculatedByRequestParamPost）

```java
// before —— 旧 SDK
DataResult r = DataApiInvoker.getCalculatedByRequestParamPost(
        new TagNamesEntity().setTagNames("AI-101"), 24, start, end, CalculationMode.Average, 3600_000L);

// after —— 公共 API
List<TagSeries> series = client.history().read(HistoryQuery.builder()
        .tags("AI-101").range(start, end)
        .mode(QueryMode.AGGREGATED).aggregation(Aggregation.AVG)
        .interval(Duration.ofHours(1))
        .build());
```

CalculationMode→Aggregation：Average=1→AVG、Minimum=4→MIN、Maximum=5→MAX、Count=6→COUNT、**RawTotal=9→SUM**、FirstRawValue=17→FIRST、LastRawValue=19→LAST。**SumValue=24（末−首）→ INTERVAL_SUM**（见 2.4），不是 SUM。

### 2.4 区间累计·首末差（getIntervalValueBySumTag，40 处）

```java
// before —— 旧 SDK（单区间 末−首）
Map<String,String> delta = DataApiInvoker.getIntervalValueBySumTag("RL..._SUM", start, end);

// after —— 公共 API（INTERVAL_SUM，每 tag 单点）
List<TagSeries> series = client.history().read(HistoryQuery.builder()
        .tags("RL..._SUM").range(start, end)
        .mode(QueryMode.AGGREGATED).aggregation(Aggregation.INTERVAL_SUM)
        .build());
double delta = series.get(0).getSamples().get(0).getDoubleValue();

// 或原生逃生口（与旧算法逐字节一致）
Map<String,String> d2 = ge.readIntervalSum(Arrays.asList("RL..._SUM"), start, end);
```

> **裁决说明**：生产实证 24(SumValue 单请求) ≠ 17/19(双请求末−首)（_SUM 4476.61521 vs 4476.2542；_PV 149565.6725 vs -1.29551125）。故 INTERVAL_SUM **保持 17/19 双请求**，不优化为 24 单请求。多桶累计差分用 `client.deltaHistory().read(...)`。

### 2.5 原始值反查（getRawDataByRequestParamPost，Backward）

```java
// before —— 旧 SDK
DataResult r = DataApiInvoker.getRawDataByRequestParamPost(
        new TagNamesEntity().setTagNames("AI-101"), start, end, Direction.Backward, 50);

// after —— 公共 API
List<TagSeries> series = client.history().read(HistoryQuery.builder()
        .tags("AI-101").range(start, end)
        .mode(QueryMode.RAW).direction(Direction.BACKWARD).count(50)
        .build());
```

> **count 何时必填**：设置了 `interval` 的网格（AGGREGATED / INTERPOLATED / SAMPLED）无需再填 `count`。
> GE 驱动会用 `HistorianUnit.resolveCount` 按时间窗与间隔精确推导服务端 `count`，
> 显式填写且与推导值不一致会抛 `IllegalArgumentException`；HLS / IoTDB 直接按 `interval` 下发，
> 不校验 `count`。只有 **RAW 的点数上限**（上例 `count(50)`）无法由时间窗推导，必须显式给出。

### 2.10 `getSampledByRequestParamPost` / `SampledEntity` 四形态分流

同一个符号承载 4 种完全不同的查询，必须按构造参数分流。下表由脚本回读 `reference/tl-back-enfi` 源码统计（2026-11-18，122 处 `new SampledEntity()`；方法名出现 128 处，差额为控制器透传/复用实体。§2.7 的 125 是 `ge_data.json` 的调用记录数，与源码 grep 的 128 差 3 处，属统计口径差异；形态判定以源码为准）：

| 形态 | 判别条件 | 处数 | 旧语义 | 新写法 | 等价性 |
|---|---|---|---|---|---|
| CurrentValue | `SamplingMode.CurrentValue` | 24 | 当前值 | `currentValues().read()` | 生产逐点 MATCH |
| Interpolated | `SamplingMode.Interpolated` | 55 | 等间隔插值曲线 | `history().read(SAMPLED)` | 生产 sampled 曲线 24 点 MATCH |
| Calculated+SumValue 整窗 | `SumValue` 且 `count=1`、无 `intervalMs` | 40 | 服务端单次 mode 24 的整窗末−首 | 原生 `readSampled(..., 6, 1, null, 1, 24, null)`；或公共 `INTERVAL_SUM` | **数值不等**：生产实测 mode24=4476.61521 vs 17/19=4476.2542；`_PV` 149565.6725 vs -1.29551125。要旧数值走原生 |
| Calculated+SumValue 多桶 | `SumValue` 且 `count>1` + `intervalMs` | 2 | 服务端每桶末−首序列 | 无公共等价；`readByInterval` 是桶末 LAST 相邻差（语义不同），要旧数值走原生 `readSampled(..., count, 24, ...)` | **不等价** |
| Calculated+其它 | 其它 `calculationMode` | 0 | 服务端聚合 | `history().read(AGGREGATED)` 按 2.3 映射 | 按聚合表 |
| 透传 | 参数来自请求（`CommonGeController:363-379`） | 1 | 任意 | 按调用方实参分流 | 无法静态判定 |

两个多桶调用点：`CommonGeController.getIntervalHistorianValueBySampled`（`:249-261`）与 `MesVitriolReportServiceImpl.getBzdsbb`（`:94-102`）。

```java
// 整窗 SumValue（旧 count=1）——要逐字节一致，走原生
GeNativeApi ge = client.unwrap(GeNativeApi.class);
List<GeModels.Series> exact = ge.readSampled(tags, start, end,
        6 /* Calculated */, 1L, null, 1, 24 /* SumValue */, null);

// 语义可变、数值可接受差异时才用公共 INTERVAL_SUM（17/19 双请求）
List<TagSeries> approx = client.history().read(HistoryQuery.builder()
        .tags("AI-101_SUM").range(start, end)
        .mode(QueryMode.AGGREGATED).aggregation(Aggregation.INTERVAL_SUM)
        .build());
```

> 不要把 `SumValue` 写成 `Aggregation.SUM`：SUM 对应 mode 9（算术和），SumValue=24 是区间末−首。两者与 `INTERVAL_SUM` 都不是同一个数。

### 2.11 区间累计类旧方法逐一替换（差值列表，不是曲线）

旧 SDK 里带 `IntervalValue` 的方法返回的都是**差值列表**，名字里的 Sampled/Interpolated 只表示取边界值的方式。逐个对照：

| 旧方法 | 旧实现（源码 `DataApiInvoker.java`） | 公共最接近 | 语义差异 | 迁移建议 |
|---|---|---|---|---|
| `getHistorianIntervalValueBySampled` | `:476-536`：sampled(Interpolated, queryModifier=1)，窗口 `end+interval`、`count+1`；逐对 `next−current`，BAD→0、跨当前时刻用实时值补、两位小数；差值挂在区间起点 | `deltaHistory().intervalDeltas(tags, metaTime, total, totalUnit, interval, intervalUnit, fill, direction, maxPoints)` | 本 SDK 是桶末 LAST 相邻相减；不插值、不补实时值、BAD 不当 0、不舍入；`tail` 丢弃；缺基线/缺值置 `missing`，回落置 `reset`；时间戳取桶样本时间 | 业务能接受新口径→`intervalDeltas`；必须复刻旧数值→保留业务侧后处理循环 |

```xml
</dependency>

```

> 旧 SDK 的 fastjson/hutool 传递依赖随之移除；新 SDK 的主依赖是 Hutool（HTTP/文本）+ fastjson（JSON，safeMode 开、AutoType 关）。业务若仍用其他库做转换，自行保留其依赖（与 SDK 无关）。

### 4.2 配置（yml）

```yaml
# before —— ge.datacollection.*（旧 SDK 硬编码默认 + Spring 配置）
# after —— tsdb.*（凭据走环境变量，时间按生产裁决用真 UTC）
tsdb:
  default-instance: ge_main
  security:
    allow-write: false
    allow-insecure-transport: false
  instances:
    ge_main:
      type: ge
      base-url: https://172.16.176.9
      auth:
        username: ${GE_USER}
        password: ${GE_PASSWORD}
        client-id: historian_public_rest_api
        client-secret: ${GE_CLIENT_SECRET}
      timeout: { connect-ms: 5000, read-ms: 30000 }
      options:
        path-prefix: /historian-rest-api
        trust-all-certificates: false   # 内网自签名联调临时 true，生产导入根证书后关闭
        time:
          request:  { enabled: true, zone: UTC, pattern: "yyyy-MM-dd'T'HH:mm:ssXXX" }
          response: { enabled: true, source-zone: UTC, target-zone: GMT+8, pattern: "yyyy-MM-dd HH:mm:ss" }
```

> **认证线缆**（已核实）：`POST {rootUrl}/uaa/oauth/token?grant_type=password&username=..&password=..`，凭据在**查询串**（UTF-8 URL 编码），`Authorization` 头为 `clientId:clientSecret` 的 Basic 编码，body 为空、Content-Type=application/x-www-form-urlencoded。**不是表单字段**。
> **时间**：生产实证旧 SDK 输出真 UTC，故 request.zone=UTC、response.source-zone=UTC、展示 target-zone=GMT+8。若某项目 GE 本身返回 GMT+8，只改 response.source-zone，不改代码。
