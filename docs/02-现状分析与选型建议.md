# 02 现状分析与选型建议

> ⚠️ 范围变更（2026-11-09）：横河已移出本期范围，新增力控 pSpace；运行态改为“单活动实例 + 策略切换”。本文第 5–6 节横河选型/POC 为历史分析，不再作为交付依据；冲突时以 [`docs/06-范围变更与力控接入.md`](06-范围变更与力控接入.md) 为准。

> 文档版本：v1.0（2026-11-09）  
> 结论先行：**统一 SDK 的技术难点不在“调通接口”，而在“把不可比的四套模型收敛成可切换的语义”。横河与 IoTDB 不是二选一：横河解决 DCS 直连，IoTDB 解决厂级汇聚。**

---

## 1. 分析方法

1. 逐文件阅读两套参照 SDK 的 `ApiClient`、枚举、Invoker、配置、自动装配与实体模型；
2. 抽取“接口描述方式、认证、返回结构、质量码、时间格式、能力边界”六个维度做对比；
3. 对缺失的横河、IoTDB 做公开资料调研，并区分“已确认事实”与“待现场核实”；
4. 用加权评分做选型初判，但把“可用性/安全性”作为否决项而非普通加分项。

## 2. 两套参照 SDK 解剖

### 2.1 共同骨架（可直接复用的部分）

两套 SDK 虽然厂商不同，骨架高度一致：

```
枚举（path/method/参数位置/返回类型）
        │
        ▼
ApiClient.execute(module, enum, params, body)
        │  反射读取枚举元数据
        ├─ 组 URL（baseUrl + contextPath + path）
        ├─ 填参（QUERY / PATH / BODY / HEADER / FORM）
        ├─ 加认证（TokenHolder）
        ├─ 发请求（Hutool HttpRequest）
        └─ 解析（fastjson → BaseResult 子类）
        │
        ▼
XxxApiInvoker（static 便捷方法）
```

可复用的设计：
- “枚举描述 HTTP 接口”使新增接口只需加枚举，不需改客户端；
- 统一 `BaseResult` 包装；
- Token 缓存 + 本地/Redis 两种实现；
- Spring Boot 自动装配 + `spring.factories`；
- 参数位置抽象（QUERY/PATH/BODY/HEADER/FORM）。

**不可直接复用的部分**：静态单例、fastjson、无超时默认值、厂商模型直接暴露给调用方。

### 2.2 HLS 专有事实

| 维度 | 事实 |
|---|---|
| 接口数量 | 4 个：实时值、历史区间值、全部标签、token |
| 实时值 | `POST /ddb/read_ddbtagvalue`，body `TagNameListRequest`，返回 `DataResult.data.ddbTagValueList` |
| 历史值 | `POST /hdb/read_hdbtagvalue`，body `HistorianRequest`，返回 `DatasResult.data.hdbTagValueList` |
| 标签 | `GET /ddb/read_alltagname`，返回 `TagName{TagDes,TagName}` 列表 |
| 认证 | `GET /user/get_token`，userid/secretkey 放 **Header**，token 缓存 1800s 默认 |
| 历史语义 | 只能按 interval 返回 **AVG/MIN/MAX/Bound 聚合**，不能返回原始点、不能插值、不能写入 |
| 返回结构 | **宽表**：`OneTagHDBValue` 同时含 `TagValue_AVG/Bound/MAX/MIN` 与三个质量列 |
| 质量码 | BAD(0)、GOOD(1) |
| 类型码 | -3 不存在、0 BOOL、1 BYTE、2 WORD、3 DWORD、4 SBYTE、5 SWORD、6 SDWORD、7 SINGLE、8 DOUBLE、18 STRING |
| 配置 | `hls.datacollection.*`，`cacheModel=Local/Redis` |
| 已知缺陷 | `HistorianRequest.buildRequest` 中 MAX/MIN 参数写反（`HistorianRequest.java:147-148`） |

**HLS 的真实能力边界**：它更像“实时库 + 区间统计接口”，不是完整的 historian。任何“统一 SDK 必须支持原始点/插值/写入”的假设，都会在 HLS 上破产。因此公共层必须**按能力建模**。

### 2.3 GE 专有事实

| 维度 | 事实 |
|---|---|
| 接口数量 | 92 个 REST 端点 + OAuth 1 个：Data 22、Tags 13、Collectors 27、Systems 25、Alarm 5、OAuth 1（早期文档误写 99，已按源码枚举修正） |
| 数据接口 | `/v1/datapoints/{calculated,configuration,create,currentvalue,interpolated,raw,sampled,trend}`，每个多有 GET query / POST body / path 变量变体 |
| 标签 | 查询（名称掩码/最大数）、增删改、注释、属性、重命名、高级检索 |
| 认证 | OAuth2：client-id/secret + username/password，Bearer；token 默认 43199s |
| 返回结构 | **长表**：`DataResult.Data[] → DataItem.Samples[]`，`Sample{TimeStamp,Value,Quality,DataAttributes}` |
| 质量码 | BAD(0)、UNCERTAIN(1)、NA(2)、GOOD(3) |
| 时间格式 | `"yyyy-MM-dd HH:mm:ss"`（服务器本地时区） |
| 能力 | 原始、插值、采样、趋势、计算、写入、报警、采集器/系统运维 |
| 配置 | `ge.datacollection.*`，同样 `cacheModel=Local/Redis` |
| 打包 | ProGuard 混淆，保留 service/entity/config |

**GE 的真实能力边界**：接口面远大于 HLS，接近完整 historian + 运维 API；但“多、杂、厂商特有能力多”，不适合全部塞进公共接口。

### 2.4 两库关键差异（公共层必须吸收的）

| 维度 | HLS | GE | 公共层处理 |
|---|---|---|---|
| 认证 | Header userid/secretkey → token | OAuth2 client credentials + Basic | `Authenticator` SPI，每驱动实现 |
| Token 生命周期 | 1800s，提前 5s 刷新 | 43199s | 统一 `TokenManager`，单飞刷新 |
| 路径前缀 | 无 | `/historian-rest-api` | 驱动内部处理 |
| 返回结构 | 宽表（一行多指标） | 长表（多样本） | 统一拆为 `TagSeries` |
| 质量码 | GOOD=1 | GOOD=3 | `QualityNormalizer` 映射表 |
| 时间 | epoch 秒（驱动按数量级兼容毫秒，`HlsNativeApi.java:606-609`） | 本地时间字符串 | `Instant` + 时区配置 |
| 标签目录 | 全量、仅名称+描述 | 检索/分页/CRUD/属性 | `TagCatalog` 能力分级 |
| 历史 | 仅区间聚合 | 原始/插值/采样/趋势/计算 | `CapabilitySet` 协商 |
| 写入 | 无 | 有 | 默认关闭，能力声明 |
| 实例模型 | static 单例 | static 单例 | 改为实例化 |

### 2.5 参照实现的问题清单（新 SDK 必须修掉）

| 编号 | 问题 | 影响 | 处理 |
|---|---|---|---|
| P1 | `ApiClient`/`TokenHolder` 静态字段 | 同 JVM 不能多实例、多库；测试互相污染 | 改为实例字段；旧静态门面仅做兼容 |
| P2 | HLS MAX/MIN 写反 | 聚合结果错 | 不复用该 `buildRequest`；自建请求构造并加单测 |
| P3 | 默认超时 -1（不限） | 网络故障时线程永久挂起 | 强制默认值，禁止 -1（或显式告警） |
| P4 | fastjson 1.2.59 | 已知 AutoType 反序列化风险 | 新 SDK 统一 fastjson 1.2.83：关闭 AutoType、开启 safeMode、只做树解析 |
| P5 | HLS 只能全量标签 | 10 万标签 OOM/慢 | 分页/流式/缓存 + 上限保护 |
| P6 | HLS 质量码仅 0/1 | 无法表达 UNCERTAIN/STALE | 映射 + 未知码保留 |
| P7 | README 与代码不一致（HLS 版本/描述/token 默认值） | 误用 | 以代码为准，重写文档 |
| P8 | Token 本地缓存无分布式协调 | 多节点同时刷新 | 单机单飞 + 可选 Redis 锁 |
| P9 | ProGuard 混淆 | 线上排障困难 | 保留 mapping 文件；关键类不混淆 |
| P10 | 无统一错误码 | 调用方难分类处理 | `TsdbException` 体系 |

## 4. 差距分析：公共层到底要吸收什么

### 4.1 模型差距

- **宽表 vs 长表**：HLS 一行含 4 个聚合值与 3 个质量；GE 每个样本一行。公共层统一为 `TagSeries{tag, samples[]}`，HLS 在驱动内拆列。
- **质量码语义**：HLS 只有好坏两态；GE 有 UNCERTAIN/NA。统一 `Quality` 后，HLS 的 GOOD 映射 GOOD，其余映射 BAD/UNKNOWN；不能把 GE 的 UNCERTAIN 强压成 BAD。
- **类型系统**：HLS 用数字码，GE 用字符串 DataType，OPC UA 用 NodeId 类型，IoTDB 用 SQL 类型。统一 `ValueType` + 保留原类型。
- **时间**：HLS 毫秒、GE 本地时间字符串、OPC UA 的 `DateTime`（100ns since 1601）、IoTDB 可到 ns。统一 `Instant`（毫秒精度起步），驱动内转换。

### 4.2 能力差距

公共接口不能假设“所有库都能原始查询/写入”。正确做法：

```java
if (!client.capabilities().supports(Capability.RAW_HISTORY)) {
    // 走聚合，或降级，或提示用户
}
```

而不是让 `readRaw()` 在 HLS 上抛一个笼统的 `UnsupportedOperationException`。

### 4.3 运维差距

- HLS/GE 都是单 base-url；横河是 OPC UA 会话；IoTDB 是多节点。
- 需要统一的超时、重试、熔断、健康检查，但**实现放在驱动**，公共层只定义契约。
- 需要统一的指标标签，但**不能把标签名放进指标标签**（基数爆炸）。

### 4.4 安全差距

| 风险 | 现状 | 目标 |
|---|---|---|
| 凭证硬编码 | 参照工程配置里有默认账号/密码 | 全部外置，示例用占位符 |
| 传输 | HLS 可 HTTP；GE HTTPS | 默认 HTTPS/TLS；HTTP 需显式降级开关 |
| 越权写 | 无写能力 | 默认 `allow-write=false`，独立凭证 |
| 依赖漏洞 | fastjson 1.2.59 | fastjson 1.2.83 + AutoType 关闭 + safeMode + 依赖扫描 |
| 审计 | 无 | 写/管理操作审计 |
| DCS 暴露 | 无 | 网关/跳板，OPC UA 端口最小开放 |

## 5. 选型：横河 vs IoTDB

### 5.1 先明确“选型”选的是什么

原始诉求里“选型”有两层含义：

1. **DCS 直连通道选谁**：横河（因为能和 DCS 直接集成）；
2. **厂级数据底座选谁**：横河 historian、IoTDB，还是两者组合。

这两层不能用同一把尺子。DCS 直连看**实时性、协议安全、与 CENTUM 的原生契合**；数据底座看**扩展性、开放性、成本、分析生态**。

### 5.2 横河的接入路径（三种，按优先级）

| 路径 | 说明 | 优点 | 风险/限制 |
|---|---|---|---|
| **A. OPC UA（DA + HDA）** | 通过 CENTUM/ExaOPC 的 OPC UA Server 读实时与历史 | 标准协议、X.509、SignAndEncrypt、可跨网段、可 Browse、可订阅 | 现场版本是否含 UA Server/HDA 需确认；证书/策略配置复杂；许可 |
| **B. OPC DA/HDA（ExaOPC 经典）** | 通过 ExaOPC 的 DA/HDA 接口，DCOM 调用 | 存量兼容、HDA 成熟 | DCOM 安全弱、端口多、跨网段难、Windows 绑定 |
| **C. Exaquantum API/ODBC** | 从 Exaquantum PIMS 读历史/ aggregates | 适合分析与报表 | 非实时控制通道；许可；数据延迟 |

**建议**：以 A 为首选，B 作为存量备选，C 仅用于分析场景。三者都封装在 `tsdb-sdk-yokogawa` 内，通过 `protocol: opcua|opcda|exaquantum` 切换。

### 5.3 横河 OPC UA 的关键待核实项

> 公开资料不足以确认具体版本能力，以下必须现场确认，不能写死假设。

1. CENTUM VP 的具体型号/版本（R6/R7？）；
2. 是否内置 OPC UA Server，还是需 ExaOPC 网关；
3. 支持的 SecurityPolicy（None/Basic256Sha256/Aes256Sha256RsaPss…）与 SecurityMode；
4. 是否支持 OPC UA Historical Access（HDA）；历史深度、采样精度；
5. 是否支持 Browse 全量标签；命名空间与 Tag 命名规则；
6. 最大会话数/订阅数/并发读；是否影响 DCS 控制器负载；
7. 冗余服务器如何暴露（VIP/双 endpoint）；
8. 证书申请、信任列表、轮换流程；业主是否允许自签；
9. 许可（OPC UA Server/ExaOPC 授权）是否已购买；
10. 是否允许只读账号；是否允许写入（默认不允许）；
11. 网络分区：应用网到 DCS 网的防火墙端口（通常 4840）；
12. 时间同步（NTP/PTP）与时间戳精度；
13. 报警/事件是否需要（A&E）；
14. 是否需要订阅（subscription）而不是轮询；
15. 现场可用的测试标签清单与对比工具（CENTUM 趋势）。

### 5.4 IoTDB 的定位

IoTDB 不是 DCS 直连协议，它是**时序数据底座**：

- 优势：开源、水平扩展、SQL、树/表模型、批量写入、压缩、与大数据生态兼容；
- 劣势：不直接说 OPC UA/DA，需要采集器或 SDK 写入；不替代 DCS historian 的“控制侧”角色；
- 最佳角色：**厂级汇聚层**——从 HLS/GE/横河读出，写入 IoTDB，供分析/报表/算法使用；
- 接入方式：优先 `iotdb-session` 的 `SessionPool`（多节点、批量、高性能），REST 作为跨语言/网关备选；
- 版本：1.3.x 稳定，2.0 引入表模型；建议以现场已有版本为准，默认树模型（与工业 tag 命名更契合）。

### 5.5 加权评分（初判，需现场验证）

权重体现“DCS 直连 + 可用性 + 安全性”优先：

| 维度 | 权重 | HLS | GE | 横河 | IoTDB |
|---|---:|---:|---:|---:|---:|
| DCS 直连/实时性 | 25% | 3 | 2 | 5 | 1 |
| 历史数据能力 | 15% | 2 | 5 | 4 | 4 |
| 安全性 | 20% | 3 | 4 | 5 | 4 |
| 可用性/成熟度 | 15% | 3 | 5 | 4 | 4 |
| 开放性/生态 | 10% | 2 | 4 | 3 | 5 |
| 成本/许可 | 10% | 4 | 2 | 2 | 5 |
| 现场可验证性 | 5% | 4 | 3 | 2 | 4 |
| **加权分（/5）** | 100% | **2.90** | **3.55** | **4.05** | **3.45** |

计算：HLS = 0.75+0.30+0.60+0.45+0.20+0.40+0.20 = 2.90；GE = 0.50+0.75+0.80+0.75+0.40+0.20+0.15 = 3.55；横河 = 1.25+0.60+1.00+0.60+0.30+0.20+0.10 = 4.05；IoTDB = 0.25+0.60+0.80+0.60+0.50+0.50+0.20 = 3.45。

**解读**：
- 横河在“DCS 直连 + 安全”上明显领先，符合原始诉求；
- IoTDB 在“开放/成本”领先，但 DCS 直连弱，不应被当作横河的替代；
- GE 综合强，但它是 historian，不是 DCS 通道；
- HLS 能力最窄，但既有现场必须保留。

### 5.6 选型结论

1. **DCS 直连通道：选横河 OPC UA**。这是唯一能同时满足“与 CENTUM 原生集成 + 标准安全协议 + 可跨网段”的路径；前提是现场版本确认支持 UA Server/HDA。
2. **厂级数据底座：选 IoTDB（推荐）**，作为汇聚/分析层；与横河不是互斥关系。
3. **既有现场：保留 HLS/GE 驱动**，通过统一 SDK 收口，不强行迁移。
4. **不搞“一刀切替换”**：统一 SDK 的价值是“多库并存、按需切换”，不是“只留一个库”。

> 一句话：**横河解决“连得上 DCS”，IoTDB 解决“存得下、算得动”，统一 SDK 解决“换得动”。**

## 8. 本章结论

1. 两套参照 SDK 的“枚举驱动 HTTP + 统一 Result + Token 缓存”骨架可复用，但**静态单例、fastjson、无超时、厂商模型直出**必须重写。
2. HLS 与 GE 的能力差距是**结构性**的，不是接口数量问题；公共层必须能力协商。
3. 横河是 DCS 直连的正确选择；IoTDB 是数据底座的正确选择；两者组合而非互斥。
4. 横河成败取决于现场 15 个待核实项，POC 必须先于大规模开发。
5. 统一 SDK 的护城河是**契约测试 + 能力矩阵 + 原生逃生口**，不是“接口多”。
